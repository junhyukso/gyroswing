# GyroSword

아이폰 자이로를 칼자루로 쓰는 1인칭 물리 검술 프로토타입입니다 (Half Sword 방식의 물리 기반 칼).
카메라나 VR 컨트롤러 없이 **폰의 방향 센서만** 사용합니다.

## 실행

```
npm install
npm start
```

- PC 브라우저: http://localhost:8080 → **시작 (소리 켜기)** 클릭
- 아이폰: PC 화면의 QR 코드 → Safari로 열기
  1. "연결이 비공개가 아님" 경고 → **세부사항 보기 › 이 웹 사이트 방문** (내 PC가 만든 인증서)
  2. **센서 시작** → "동작 및 방향" **허용**
  3. 손목 스트랩 착용, 화면 세로 고정, 화면 앞 약 1.5m
- 연결은 **WebRTC 데이터 채널**(UDP, 폰↔PC 직접)이 우선입니다. 폰 화면 위쪽에 "WebRTC"가 보이면 정상입니다.
  - 연결 정보는 HTTPS 요청으로 주고받고, 브라우저가 숨기는 `xxxx.local` 주소는 서버가 실제 IP로 바꿔 넣습니다(mDNS·방화벽 문제 회피).
  - 센서 패킷은 순서·재전송 없는 채널로 보내서 늦은 패킷이 새 패킷을 막지 않습니다.
- WebRTC가 안 되면 WebSocket → HTTP 순으로 자동 대체됩니다. Safari는 이 PC가 만든 인증서로는 WebSocket을 막으므로,
  WebSocket을 쓰려면 `http://<PC IP>:8080/ca.crt`를 설치하고 설정 › 일반 › 정보 › 인증서 신뢰 설정에서 켜야 합니다.
- 폰 없이: **폰 없이 시뮬레이터로** (화면 클릭 → 마우스로 칼 조작, 휠 = 칼날 회전, T/Y/U/I/O = 자동 베기, P = 일부러 칼날 틀어진 베기)

## 보정 (처음 한 번, 이후엔 정면 재정렬만)

화면에 **노란 목표 칼**(칼날을 감싼 빛 기둥, 칼끝 구슬, 칼끝 앞 빛줄기)과 **위·옆에서 본 그림**이 나옵니다.
실제 폰을 그 칼과 똑같이 들고 멈추면 진행 막대가 차오르고, 다 차면 자동으로 저장됩니다.

1. 정면 겨누기(화면 가운데 과녁) → 2. 칼 세우기 → 3. 오른쪽 앞 45° → 4. 왼쪽 앞 45° → 5. 위쪽 앞 45° → 6. 아래쪽 앞
7. **확인**: 이제 실제 칼이 보입니다. 손과 같으면 폰 화면 탭(또는 Enter), 어긋나면 길게 눌러 다시 합니다.

- 보정하는 동안에는 실제 칼을 숨깁니다. 아직 보정되지 않은 칼을 보며 맞추면 틀린 값에 손을 맞추게 되기 때문입니다.
  대신 칼끝 높이(중력으로 정확히 앎)가 목표와 다르면 "더 올리세요/내리세요"라고 알려줍니다.
- 6자세 전체로 그립과 정면 방향을 최소제곱으로 계산합니다. 자세를 최대 8°쯤 대충 따라 해도 오차가 2자세 방식의 절반 정도이고, 영 다르게 든 자세 하나는 자동으로 빠집니다.
- 정면 겨누기 자세에서는 모니터 높이에 따라 겨누는 각도가 다르므로 높이는 실측값을 쓰고 좌우 방향만 씁니다.
- 전체 보정은 앞이 트인 자리로 잠깐 이동해서 하고, 끝나면 원래 자리로 돌아옵니다.

## 베기 수련 (5번)

종목 9가지: 수평베기 ←, 수평베기 →, 수직 내려베기(눕힌 짚단), 사선 내려베기 ↙, 역사선 ↘, 올려베기 ↗, 역 올려베기 ↖, 찌르기(과녁), 연속베기(↙ 다음 2초 안에 ↘).
짚단 위의 하늘색 화살표가 베어야 할 방향이고, 실제로 칼날이 지나간 방향(플레이어가 보는 면에서의 각도)이 ±25° 안이면 성공입니다.
틀리면 "수평베기(←)로 판정"처럼 실제 동작을 알려 주고, 오른쪽 위에 성공/시도와 평균 방향 오차가 쌓입니다. 찌르기는 과녁 빨간 고리(7cm) 안 + 칼날 방향 이동 + 2.5m/s 이상.

## 막기 수련 (6번)

목각 기사가 **진짜 물리 칼**(플레이어 칼과 같은 힘 제한 서보)로 공격하므로 칼끼리 실제로 부딪히고 밀립니다.
공격 6가지: 정수리 내려베기, 왼쪽/오른쪽 위 사선베기, 왼쪽/오른쪽 수평베기, 찌르기. 예비동작(칼을 들어 올리는 동안)에
하늘색 화살표(베기 방향, 머리 또는 몸통 높이)나 고리(찌르기)가 떠서 어디로 올지 알려 줍니다.

| 단계 | 예비동작 | 판정 |
|---|---|---|
| 1 초급 | 0.95초 | 칼을 공격선에 두기만 해도 막힘 (상대가 물러남) |
| 2 중급 | 0.7초 | 손잡이 쪽 절반(강)으로, 칼끼리 40° 이상(찌르기는 25°)이어야 막힘. 아니면 물리로 밀림 |
| 3 상급 | 0.5초 | 가만히 대면 힘(800N)에 밀려 맞음 → **마주 쳐내야** 함 |
| 4 실전 | 0.45초± | 3단계 힘 + 무작위 순서 + 35% 확률 연속 공격 |

- **쳐냄(패리)**: 부딪히는 순간(또는 직전 80ms 안)에 **내 입력(목표 칼)**이 상대 칼 쪽으로 1.5m/s 이상 움직이고 있었으면 인정.
  손잡이 근처에서 닿아도 손목 스냅은 칼 가운데(35cm) 기준 속도로도 봅니다(폰은 팔이 미는 걸 거의 못 봄).
  칼이 이미 맞닿은 채로(바인드) 공격이 시작되면, 공격 중에 쳐내면 쳐냄으로 바뀝니다. 물리 칼이 밀렸다 되튀는 속도는 안 셉니다.
  상대가 비틀거리며(토크 25%) 물러납니다.
- 1·2단계에서 잘 막으면 상대가 칼을 멈춥니다(관성으로 미끄러져 들어오지 않음).
- 막은 곳(손잡이 쪽 / 가운데 / 칼끝 쪽)과 두 칼 사이 각도가 매번 표시되고, 오른쪽 위에 방어·막음·쳐냄·피격이 단계별로 쌓입니다.

### 막기 자세 → 손 위치 (팔 모델의 막기 층)

실제 막기 녹화(2026-10-15)에서 본 것: 막을 때는 **팔 전체가 공격 오는 쪽 바깥으로** 나가고 **날이 공격 쪽을 향합니다**.
칼 방향만으로는 이걸 알 수 없습니다. 오른쪽 막기는 칼끝이 왼쪽 위를 향해 몸 앞을 가로지르는데, 칼 방향만 보는 팔 모델은 이걸 "손이 왼쪽"으로 읽었습니다.
그래서 칼 방향 + 날 방향(전체 자세)이 녹화에서 뽑은 막기 자세(`BLOCK_POSES`)에 가까우면(20°까지 100%, 40°에서 0) 손을 그 막기 자리로 보냅니다.

| 막기 자세 | 칼 / 날 | 손 |
|---|---|---|
| 왼쪽 (왼쪽 사선·수평) | 세워서 앞으로 기울임 / 날 왼쪽 | 왼쪽 바깥 (x −0.34) |
| 오른쪽 위·아래 (오른쪽 사선·수평) | 칼끝 왼쪽 위로 몸 앞 가로지름 / 날 오른쪽 위 | 오른쪽 바깥 (x +0.30) |
| 정수리 | 눕혀서 왼쪽 앞 / 날 위 | 이마 위 (y 1.72) |
| 찌르기 | 눕혀서 몸 앞 가로지름 / 날 앞오른쪽 | 가슴 앞 약간 오른쪽 |

- **옆 막기는 자세가 아니라 의도로**도 잡습니다: 공격이 오는 쪽(게임이 앎)으로 **칼이 기울었거나 날이 그쪽을 향하면** 손을 그쪽 바깥(x ±0.34)으로.
  오른손잡이는 오른쪽에서 팔을 거의 안 빼고 칼만 바깥으로 기울이거나 손목만 돌려 날을 오른쪽으로 향합니다(2번째 녹화). 기본 경계 자세 그대로면 안 움직입니다 (설정 `blockSide`).
- **공격이 오고 있을 때만** 켜집니다(예비동작부터 공격이 끝날 때까지).
  설정 G › 떨림 억제 · 팔 개입 › **막기 자세 항상 켜기**를 켜면 공격이 없을 때도 쓰입니다. 이때는 칼을 멈춰 들거나 천천히 움직일 때만
  (회전 3~6 rad/s부터 풀림) — 막기 자세에서 바로 휘둘러 나가도 휘두르는 순간 기본 팔 모델로 넘어가고, 녹화 재생상 칼 튐은 그대로입니다.
  (공격이 없으면 공격 방향·높이를 모르므로 '의도 기반 옆 막기'와 높이 보조는 빠지고, 녹화에서 뽑은 막기 자세만 적용됩니다.) 백핸드로 베기 직전 자세가 오른쪽 막기와 같아서, 늘 켜 두면 베기 준비 때 손이 튑니다
  (베기 녹화 4개에서 2~4.5% 시간 오인식 → 이 조건으로 0%). 아주 빠른 스윙(10~16 rad/s)에서는 풀립니다. 쳐내기 스냅(5~10 rad/s)은 유지합니다.
- **막기 높이 보조**: 머리 막기와 몸통 막기는 손목 각도가 같고 손 높이만 달라서 자이로로는 구분이 안 됩니다. 게임은 공격 높이를 알기 때문에,
  막기 자세일 때만 칼의 강한 쪽(손잡이에서 15~45cm)이 그 높이를 지나도록 손을 위아래로 최대 25cm 옮깁니다 (설정 `blockAssist`, 0이면 끔).
  높이는 실측값: 수평베기 1.0m(옆구리), 사선 1.65m, 정수리 1.75m, 찌르기 1.1m.
- 녹화 그대로 재생한 결과 (공격 17번, 1단계): 이전 팔 모델 **5/17** → 지금 **16/17** (타이밍 ±0.15초에도 15~17), 2단계 16/17, 3단계 2/17(가만히 대면 밀리는 게 정상).
  같은 자세에 손목 스냅(35°)을 넣으면 3단계에서 7~13/18 쳐냄. 가만히 막았는데 쳐냄으로 잡히는 경우 0.

## 손 위치와 베기 판정

- **손 위치 = 팔 모델(칼 방향 → 손 위치) + 보정.** 보정은 "가속도로 잰 실제 손 속도 − 팔 모델이 예상한 손 속도"를 적분한 값입니다.
  찌르기(칼 방향은 그대로, 손만 이동)는 그대로 들어가고, 손목 스윙(팔 모델은 손이 움직인다고 보지만 실제론 제자리)은 손이 제자리에 남습니다.
  회전이 빠를 때는 60Hz 적분이 부정확하므로 "팔 개입도 × 팔 모델 속도"를 대신 씁니다.
- **팔 개입도**: 스윙 중 손(폰)의 최고 이동 속도(마지막 정지 시점부터 가속도 적분). 실측: 손목 스윙 1.0~1.4m/s, 팔 스윙 2.5~3.5m/s → 1.4~2.8m/s 사이를 0~100%로.
  (회전 반경 가속도/ω²는 구분이 안 됐습니다: 큰 스윙도 끝에 손목을 꺾어서 ω가 크게 나옵니다.)
- **베기**: 칼날 정렬 + 물리 칼 접촉점 에너지 ½·m·v² ≥ 70J. m은 손목 0.35kg ~ 팔 1.5kg(팔 개입도로 보간).
  실측 녹화 기준 큰 팔 스윙 15/15 베임, 손목 스윙 2/42만 베임 (`tools/physics-replay.mjs`).

## 성능

측정 (이 PC, RTX 5080, `public/qa/perfbench.js`): CPU 1~2.5ms/프레임 (짚단 42번 베기 중에도 중앙값 2.4ms), GPU 아래 표.

| 화질 | 내용 | GPU 1080p | 1440p | 4K |
|---|---|---|---|---|
| 높음 | GTAO(절반 해상도) · 그림자 4096 · 블룸 · SMAA | 0.7ms | — | 2.4ms |
| 중간 | GTAO 끔 · 그림자 2048 · 픽셀 비율 ≤1.25 | 0.36ms | 0.47ms | 0.96ms |
| 낮음 | 블룸도 끔 · 그림자 1024 · 픽셀 비율 1 | 0.29ms | 0.37ms | 0.79ms |

- **자동 화질**(기본): GPU 시간(타이머 쿼리, 3프레임마다)이 화면 주사율 예산(프레임 간격의 75%)을 1.5초 넘으면 한 단계 내리고,
  예산의 30% 미만이 6초 이어지면 올립니다(내린 단계는 2분간 다시 안 올림). 타이머가 없는 브라우저는 놓친 프레임 비율로 내리기만 합니다.
- GTAO는 원래 4K GPU 시간의 ~80%였습니다 → AO 계산·노이즈 제거만 절반 해상도로 (깊이·법선은 원본): 4K 4.4→2.4ms, 화면 차이는 평균 0.8/255.
- **칼 보간**: 물리는 240Hz 고정이라 144/165Hz 화면에서는 프레임마다 1~2스텝씩 진행돼 빠른 칼이 떨려 보였습니다.
  이제 마지막 두 물리 상태 사이를 그립니다(지연 4ms 고정). 칼끝 이동 불균일 144Hz 43%→11%, 165Hz 60%→10% (`public/qa/judder.js`).
  상대 기사의 칼도 같고, 궤적(트레일)은 그려진 칼에서 끝납니다.
- 물리 스텝마다 만들던 객체(궤적 샘플, 상대 칼 목표, 속도 계산)를 재사용으로 바꿔 가비지 컬렉션 부담을 줄였습니다.

## 칼 튐 (네트워크 끊김)

녹화 분석(2026-10-15, PC·폰 둘 다 Wi-Fi): 샘플의 5~9%가 50ms 넘게 늦고, 100~350ms 통째로 끊기는 일이 분당 수십 번
(끊김 길이가 ~100ms 배수 → PC 무선랜이 절전으로 비콘마다 깨어나는 패턴). 화면의 칼이 튀던 원인과 처리:

- **끊김 중 칼 폭주 (버그)**: 예측은 멈췄는데 서보의 속도 선행값은 마지막 회전속도 그대로 → 물리 칼이 혼자 초속 수 m로 날아가다
  '칼 위치 복구'로 순간이동(최대 1m). 이제 선행값은 예측이 실제로 움직이는 만큼만(`Fusion.advance`).
- **휘두르다 막기 자세를 스치면 손이 튐**: 예전 막기 손 배치(크라운/옆/행잉)가 항상 켜져 있어 0.7m 스파이크 → 공격이 올 때만.
- **끊김 처리**: 끊긴 동안 마지막 실측으로 되돌아가던 것(뒤로 한 번, 데이터 오면 앞으로 한 번 튐) → 예측 유지 + 60ms 감속 연장,
  늦게 몰려온 데이터의 보정은 20ms에 걸쳐 (`smoothMs`, `staleHold`, `staleExtraMs`, `snapDeg`).
- **무선 깨우기**: 게임이 10ms마다 1바이트를 폰으로 보내 PC 무선이 졸지 않게 (WebRTC 연결일 때).
- 결과 (`node tools/physjumps.mjs <녹화>`, 화면에 그려지는 물리 칼 기준): 29초 녹화 칼끝 튐 215→100cm/분, 2분 38초 녹화
  회전 튐 140→85°/분, 1m 순간이동 없음. 남은 큰 튐은 데이터가 통째로 없는 긴 끊김(150~350ms) 동안 실제로 움직인 만큼이라
  네트워크로만 줄일 수 있습니다:
  - PC: 장치 관리자 › 네트워크 어댑터 › Wi-Fi(MediaTek) › 고급 › **Power Saving → 사용 안 함**, **로밍의 주동성 → 최저**
  - 또는 PC를 **유선 LAN**으로 (무선 구간이 폰 쪽 하나로 줄어듦)
  - H 디버그 화면의 `지연(중앙/95%)`의 95% 값이 낮아지면 효과가 있는 것
- `node tools/jumps.mjs <녹화> [--sweep]` — 융합 자세 기준 튐·정확도 (설정 비교), `node tools/physjumps.mjs <녹화> --trace t0 t1` — 구간 추적

## ZIG SIM 모드 (ARKit으로 실제 손 위치)

자이로·가속도만으로는 손 위치를 알 수 없어서(가속도 적분은 기본 자세 복귀마다 15~23cm 어긋남, `tools/zupt.mjs`),
iOS 앱 **ZIG SIM Pro**가 보내는 애플 ARKit 위치를 씁니다. 사파리 컨트롤러 대신 이 앱을 켜 두면 게임이 그걸로 조작됩니다.

**앱 설정**: Protocol UDP · IP = PC 주소 · Port **50000** · 형식 OSC 또는 JSON(둘 다 받음) · 60 FPS ·
센서: **ARKit (DEVICE)**, Quaternion, Gyro, Accel, Gravity, **Touch** → Start. 사파리 페이지는 쓰지 않습니다(앱이 앞에 있어야 ARKit이 돎).

- **방향**: Core Motion 자세(쿼터니언·자이로)를 기존 융합·보정·팔 모델에 그대로 넣습니다(`Fusion.pushAttitude`).
  규약은 녹화로 맞춤(`tools/zig-frames.mjs`): 자세 = 폰→기준, 자이로 = 폰 좌표, 사용자 가속도는 g 단위·부호 반대,
  ARKit 카메라 = 폰 좌표를 z축으로 +90°.
- **손 위치 (하이브리드, `arkit.js`)**: ARKit 렌즈 위치 → 손잡이 위치(렌즈에서 약 9cm) → 몸 기준 좌표.
  - **믿는 때만** 씁니다: ARKit 속도가 사람 손으로 가능하고(<2.5m/s), 팔 길이 안이고(가슴에서 15~85cm — 몸통 속이면 표류),
    방금 튀지(재인식) 않았을 때. 막기 수련 녹화에서 막기 자세로 옮기는 순간(3~8 rad/s) 0.1~0.25초 뒤에 공격이 닿아서,
    빠른 움직임 자체로는 끊지 않습니다(4~8 rad/s 사이에서 서서히, 0.06초면 다시 믿음).
  - **'눈 감고 움직임'**: ARKit이 표류한 건 특징점이 적은데(12개 미만) **계속 휘두를 때**였습니다(빈 천장을 지나 1.5~3초,
    몇 초에 2m). 그런데 칼을 위로 드는 것만으로도 카메라가 천장을 봐서 특징점이 1~16개로 떨어지고(베기 연습 녹화),
    예전엔 그때마다 끊어서 높은 막기·베기 준비 자세가 안 잡혔습니다. 이제는 특징점 적은 움직임(1.5 rad/s 또는 0.4m/s 넘게)을
    얼마나 빠른지로 가중해 쌓고(잘 보이면 0.5초, 아니면 1초에 걸쳐 잊음) 0.5초어치가 넘어야 0.4초 끊습니다. 그 뒤엔
    0.2초 안정되거나 특징점 25개 넘게 0.3초 보일 때까지 기다립니다. 손 보정은 0.5초에 걸쳐 풀립니다.
  - 베기 연습 녹화: ARKit 믿는 시간 38% → 59%, 손이 높을 때(1.15m 위) 41% → 78%. 예전 표류 녹화의 표류 구간은 그대로 0%.
  - 그 녹화를 새 설정으로 게임에 재생(`blockharness.js` `replayZig`): 1단계 9번 중 막음 3 → 막음 5 + 쳐냄 1.
  - **기준점**: ARKit은 방 안 위치라 몸이 움직이면 손이 움직인 걸로 보입니다. 처음 칼을 앞으로 겨누고 멈춘 자세를
    '기본 자세'로 기억하고, 그 자세(날 방향 포함 20° 이내)로 돌아올 때마다 기준을 다시 맞춥니다(그 자세에선 팔 모델이 기준).
- **막기 보정 꺼짐**: ARKit 기준이 잡혀 있는 동안은 막기 보정(막기 자세 인식·공격 방향 쪽 손 보내기·높이 맞추기·예전 막기 손 배치)을
  전부 끕니다 — 실제 위치만으로 막습니다(설정 `assistWithArkit`=true면 ARKit을 못 믿는 순간의 대체로 유지). 단계별 판정 규칙은 그대로.
- **터치**: 짧게 = 탭(확인·다음), 길게 = 재정렬 — 사파리 페이지와 같은 동작. 전체 재보정은 PC에서 C(또는 확인 단계에서 길게).
  ZIG SIM(OSC)은 손가락이 닿아 있는 동안만 `touch01`(x)·`touch02`(y)·`touchradius0`·`touchforce0`를 값 하나씩 보냅니다.
- 녹화 재생 결과(`tools/zig-replay.mjs`): 왼쪽 막기 손 x −28cm, 오른쪽 +38cm, 머리 위 높이 +24cm(팔 모델만으로는 0),
  휘두르는 동안 ARKit 신뢰 0%, 기본 자세 보정 0cm.
- 도구: `tools/zig.mjs`(ARKit 품질), `tools/zig-frames.mjs`(좌표 규약), `tools/zig-replay.mjs`(하이브리드 재생 —
  `--timeline`에 못 믿는 이유 B 눈감음·S 안정 대기·W 휘두름·J 튐·R 범위 밖·G 기본 자세, `--set=키=값`으로 변수 시험,
  `--seg=a-b` 구간 신뢰율), `tools/zig-drift.mjs`(기본 자세로 돌아올 때마다 ARKit 손과 팔 모델의 차이 = 표류),
  `tools/zig-send.mjs <녹화> [포트]`(녹화를 UDP로 다시 보내 실기 없이 시험 — 시험용 서버 `--zig 50001`로).
  서버는 세션마다 처음 30개 원본을 `recordings/zigsim-raw.txt`에 남깁니다.

## 대결 (로컬 멀티플레이) — `http://localhost:8080/duel`

두 사람이 각자 폰으로 보정하고 물리 칼로 겨룹니다. 칼끼리는 실제로 부딪혀 막히고 밀리며, 상대 몸에 맞은 칼은
얼마나 세고 깨끗하게 들어갔는지로 피해를 줍니다.

- **접속**: 화면에 1P·2P QR이 따로 나옵니다. 각자 자기 QR로 폰을 열면(`/phone?seat=…`) 서버가 그 폰을 그 자리로만
  보냅니다. ZIG SIM이면 그 자리의 **ZIG SIM으로 연결**을 누르고 그 폰 화면을 터치합니다(그 폰이 그 자리 것이 됨).
- **한 컴퓨터**: 화면을 반으로 나눠 각자 1인칭. 2P의 보정은 따로 저장됩니다(`.p2`).
- **두 컴퓨터**: 2P 컴퓨터 브라우저로 2P 칸에 적힌 주소(`http://<IP>:8080/duel?join=<방>`)를 엽니다. 2P의 폰 연결·보정·
  입력은 2P 컴퓨터에서, 물리와 판정은 1P 컴퓨터(방장)에서 하고 2P 화면은 방장이 보내는 상태(60Hz)를 그립니다.
  2P가 들어오면 방장 화면은 1P 전체 화면으로 바뀌고, 나가면 다시 화면 분할로 2P를 받습니다.
- **진행**: 폰이 연결되면 바로 보정(전에 보정했으면 정면 재정렬만) → 각자 폰 **탭** = 준비 → 3·2·1 → 대결.
  체력 100, 0이 되면 라운드 승, **2라운드 먼저 이기면** 최종 승리. 다시 하려면 둘 다 탭.
- **폰 조작**: 탭 = 준비 · **두 번 탭 = 전체 보정** · 길게 = 정면 재정렬 · 끌기 = 이동(사파리 컨트롤러).
  키보드(방장): 1P F 준비 · C 보정 · Space 재정렬 · WASD 이동 / 2P J · N · Enter · 방향키.
- **판정** (`duel.js` `hit`): 내 칼이 상대 몸(몸통·머리)에 **새로 닿는 순간**의 그 칼 자체 속도로 —
  베기 = 칼날에 수직인 속도, 날 정렬(칼등이면 35%), 팔 개입도(손목만이면 가볍게)로 에너지 → 피해(최대 35, 머리 ×1.5).
  찌르기 = 칼끝 쪽이 칼날 방향으로 들어간 속도(팔 질량, 20 J 기준). 가만히 든 칼에 상대가 걸어 들어온 건 피해 없음.
- **거리·내딛기**: 1.8m에서 시작(기본 자세 칼끝이 상대 몸에 닿지 않는 거리). 세게 휘두르면(칼끝 5→12 m/s) 몸이 최대
  0.4m 내딛어 베기가 닿습니다(시뮬레이터 베기 도달 1.3~1.5m + 내딛기). 서로 마주 보게 자동으로 돕니다.
- **화면**: 각 플레이어 카메라는 자기 층만 봅니다 — 상대 기사(팀 색 겉옷)는 상대 카메라에, 내 1인칭 팔은 내 카메라에,
  보정용 금색 칼도 그 사람 화면에만. 화면 분할 땐 AO(GTAO)를 끕니다.
- 서버: 자리별 중계(`?seat=`), 방(`/ws?role=duel&room=`)으로 방장↔2P 메시지 전달, ZIG SIM 폰(uuid)별 주인 자리.
- QA: `/duel?sim` — 두 자리 모두 시뮬레이터(보정까지 자동), 콘솔 `duel.tap(0); duel.tap(1)` → 대결,
  `duel.sim(0).swing('vertical'|'diagonal'|'horizontal'|'thrust'|'rising')`, `duel.eventLog`(부딪힘·적중 기록).
  두 컴퓨터 시험은 한 브라우저의 두 탭으로: 방장 `/duel?sim&pump`, 2P `/duel?join=<duel.room>&sim&pump`
  (`?pump`: 뒤에 있는 탭도 60Hz로 도는 QA 루프).

## 폰 카메라 진단 (손 위치 추적 가능성)

자이로·가속도만으로는 손 위치를 알 수 없어서(가속도 이중적분은 0.3초면 쓸 수 없음), 폰 카메라로 위치를 추적(SLAM)할 수 있는지
먼저 잽니다. 폰 화면의 **📷 카메라 진단**: 뒷카메라(앞/뒤 전환 가능) 매 프레임의 선명도·특징점 칸 수(160×120을 8px 칸으로,
추적 가능한 모서리가 있는 칸, 300칸 중)·밝기·fps를 그 순간 회전속도와 함께 PC로 보내고, 1초마다 작은 사진도 보냅니다
(PC 화면 왼쪽 아래에 표시, F9 녹화에 저장). 분석: `node tools/camprobe.mjs [녹화]` → 회전속도 구간별 품질, 멈춘 자세 품질,
사진은 `recordings/<녹화>-cam/`에.

## 개발

- `npm test` — 수학/보정/융합 단위 테스트
- `npm run bench` — 휘두르기별 오차·지연·칼끝 속도
- `http://localhost:8080/?timer` — 탭이 가려져도 루프가 도는 QA 모드, `?q=low` — 저사양 렌더
- `?manual` — 아무것도 저절로 돌지 않고 `game.advance(ms)`로 가상 시간을 진행 (결정적 QA, 폰으로 메시지 안 보냄)
- `node tools/analyze.mjs [녹화파일] [--known-map]` — 녹화 분석: 센서 주기·지연·자이로 축·실제 데이터 기준 예측 오차
- `node tools/replay.mjs [녹화파일] [--compare|--sweep]` — 녹화를 240Hz로 재생해 정지 떨림·스윙 오차·손 이동량 채점
- `node tools/thrusts.mjs [녹화]` — 녹화에서 찌르기 같은 강한 가속 동작을 찾아 방향·회전·이동량 표시
- `node tools/eval-thrust.mjs <찌르기 녹화> <휘두르기 녹화>` — 이동(찌르기) 설정별로 찌르기 도달 거리와 휘두를 때 가짜 이동 비교
- `node tools/eval-hand.mjs <찌르기 녹화> <휘두르기 녹화>` — 손 모델별 찌르기 도달·손목 스윙 칼날 속도·정지 시 밀림 비교
- `node tools/physics-replay.mjs <녹화> [J]` — 녹화로 물리 칼을 움직여 스윙별 베기 에너지와 기준 통과 수 (실제 판정과 같은 방식)
- `node tools/swing-stats.mjs <녹화...>` — 스윙별 최대 회전속도·가속도·손 속도 비교 (손목/팔 녹화 비교용)
- `node tools/blocks.mjs [녹화] [--timeline] [--json out]` — 막기 녹화에서 멈춘 막기 자세(칼·날 방향, 팔 모델 손 위치, 가속도 이동량)와 공격 순서 추정
- `node tools/block-events.mjs [녹화]` — 공격 이벤트가 든 녹화에서 공격마다 시작·중간 시점의 칼/날 방향, 손 위치, 막기 가중치, 가장 가까운 막기 자세
- `node tools/block-fp.mjs <녹화...>` — 막기 층이 켜진 시간 (베기 녹화에서 0이어야 함, `ALWAYS=1`이면 공격 조건 없이)
- 브라우저 QA (`?manual` 페이지 콘솔): `const H = await import('/qa/blockharness.js'); await H.setup();` →
  `H.run(단계, n, 자세)`(시뮬레이터가 예비동작 동안 막기 자세를 잡음), `H.replay('rec-….json', holds, {level, lead})`(녹화를 원래 타이밍으로 게임에 재생, 서버의 로컬 전용 `GET /rec/<이름>`),
  `H.replayEvents('rec-….json')`(공격 이벤트가 든 녹화: 공격도 기록된 그 시각·종류·단계로 — 실제 결과와 거의 같게 재현됨)
- F9 녹화에는 막기 수련의 공격 시작·결과 이벤트도 같이 저장됩니다 (`events[].type === 'drill'`)
